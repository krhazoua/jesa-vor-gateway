                                                                                        1.        Introduction
                                                                                        The NAMUR Open Architecture (NOA) concept set out in NE 175 [1] has the goal to leverage innovative and
                                                                                        efficient standard IT technologies for the industrial process automation.
                                                                                        The core principle behind NOA is to offer legacy automation architectures secure access to modern IT
                                                                                        architectures and technologies without requiring invasive modifications and without compromising safety,
                                                                                        security or reliability [2]. NOA’s key principles are [3, 2]:
                                                                                             •   NOA is complementary (additive) to existing automation architectures;
                                                                                             •   NOA is open for new approaches within the next generation of automation technologies;
                                                                                             •   NOA is based on existing open standards and technologies;
                                                                                             •   NOA enables the rapid integration of highly volatile IT components in everything encompassing the field
                                                                                                 layer, supervisory control layers all the way to enterprise level;
                                                                                             •   NOA reduces costs of information availability by using open, scalable and integrative approaches;
                                                                                             •   NOA does not pose or introduce threats to the reliability, availability and security of the plant in which it
                                                                                                 is used.

                                                                                        (red squares) as defined by NE 175 ([1], Figure 3). Note that the deviating position and direction of VoR
                                                                                        as well as its data streams as shown by NE 175 are specified in detail by this specification (see Figure
                                                                                        2).
                                                                                        NOA domains and components are defined in [1]. NOA’s security zones & associated concepts are defined in
                                                                                        [4]. Concepts from these sources that are referenced throughout this document are briefly described below.

                                                                                        The NOA concept introduces the following communication domains (see Figure 1):
                                                                                           • The core process control (CPC) communication domain houses all production- and safety-critical
                                                                                              systems. In legacy/brownfield plants, the CPC contains the automation pyramid layers [2]. In greenfield
                                                                                              plants, the CPC domain can also contain architectures such as O-PAS [5] or modular automation
                                                                                              components as per VDI 2776 [6].
                                                                                             •   The plant-specific monitoring and optimization (psM+O) communication domain, colloquially referred to
                                                                                                 as a second communication channel [7], allows processing of data and information from the CPC and
                                                                                                 making it available for arbitrary use. IT is owned and controlled by the plant owner/operator [4].



                                                                                                                                             Page 7 of 59
                                                                                        NE 178                               NOA Verification of Request                           Version 2025-03-10



                                                                                             •   The central monitoring and optimization (usually abbreviated as M+O) domain represents and provides
                                                                                                 applications outside the owner’s/operator’s control, providing insights, additional information,
                                                                                                 optimization or similar benefits as a third-party service [7].
                                                                                        The NOA concept allows information from both M+O domains to be integrated back into the core process control
                                                                                        for optimizing the operation of the plant [8]. The NOA Verification of Request (VoR) component of the NOA
                                                                                        concept described in this document provides recommendations on how to achieve this reintegration safely and
                                                                                        securely while maintaining a high degree of flexibility.
                                                                                        Section 6 of this Recommendation introduces the overall VoR concept, components, actors as well as their key
                                                                                        attributes and requirements.
                                                                                        Section 7 specifies in detail each step required to be performed for reintegrating information.
                                                                                        Section 8 reconsiders interfacing VoR with M+O and CPC components, e.g., request contents, security aspects
                                                                                        of communication, etc.
                                                                                        Annex A provides supplementary information and detailed tables for the previous sections.
                                                                                        Annex B: VoR Use case studies provides examples of how specific problems could be solved using VoR,
                                                                                        including examples of which technical systems might be involved in the various steps.
                                                                                        Manufacturers utilizing “NOA Verification of Request” (or abbreviations thereof) to promote their products and
                                                                                        technologies should ensure compliance with all mandatory requirements in this Recommendation. This
                                                                                        Recommendation does not constitute a certification of any kind, expressed or implied. Whenever necessary,
                                                                                        security implementations pertaining to process automation systems should be certified in accordance with
                                                                                        national and international standards.

                                                                                        2.        Aim
                                                                                        A Verification-of-Request component within NOA is an information technologies (IT) system-of-systems
                                                                                        architecture. Using VoR allows the automation of optimizing a production process in a beneficial manner by
                                                                                        automating the steps that real-world experts would go through when they reintegrate requests for change.
                                                                                        VoR’s expressed goals are
                                                                                             1. to maintain the integrity, safety, reliability, and security of the CPC domain by any means necessary
                                                                                                while allowing information to traverse the domain boundaries in a well-defined, controllable, repeatable,
                                                                                                automated and traceable fashion;
                                                                                             2. to enable information to be submitted to or acquired in NOA (plant specific or global) M+O domains
                                                                                                using vendor-agnostic interfaces built on open, established, and available technologies;
                                                                                             3. to enable said information to traverse the boundary to the CPC domain;
                                                                                             4. to facilitate the interpretation, verification, and CPC-specific processing of the information provided by
Normen-Download-DIN Media-Imrane NEJAM-KdNr.8456219-LfNr.11476178001-2025-05-16 12:42




                                                                                                the M+O domains;
                                                                                             5. to enable components within the CPC domain to interpret the information contained in a request in a
                                                                                                manner that is beneficial, understandable to and trusted by the underlying controlled process;
                                                                                             6. to enable components of the VoR architecture to provide limited, well-defined feedback to the submitter
                                                                                                of a request pertaining to the processing status of the request.

                                                                                        3.        Scope of application
                                                                                        This document is directed at owners and engineers of brownfield (classical), greenfield (new) and modular
                                                                                        production process plants as well as at IT staff administrating such sites.
                                                                                        This document details how the NOA Verification of Request can set up an information pathway linking the M+O
                                                                                        domains to components of the core process control. To this end, the Recommendation details an architectural
                                                                                        concept that explains how VoR is structured and what processing steps are performed so that information can
                                                                                        traverse the boundary between plant-specific M+O and CPC. It provides further details on both mandatory
                                                                                        requirements and optional attributes of such a VoR architecture.
                                                                                        The concepts of this Recommendation hold particular relevance for manufacturers and/or vendors of automation
                                                                                        solutions, which are intended to be used within production processes and which either (a) interact with VoR or
                                                                                        (b) incorporate components of the VoR concept.

                                                                                                                                           Page 8 of 59
                                                                                        NE 178                              NOA Verification of Request                          Version 2025-03-10



                                                                                        To enable manufacturers and vendors to keep pace with the rapid developments of IT technologies and benefit
                                                                                        from new technologies arising over time, this Recommendation does not mandate any specific technologies,
                                                                                        information models or communication formats. Where required for interoperability, information interfaces are
                                                                                        constrained (see section 8.1 Information interfaces). Where not required, VoR concepts should be tailored to be
                                                                                        interoperable with existing and new automation solutions at the discretion of the VoR manufacturer.
                                                                                        VoR was designed to be applicable to any production process or production facility in all life-cycle stages of a
                                                                                        facility. For greenfield and modular production processes VoR is pertinent to the design, engineering and
                                                                                        operational phases of the life cycle of a facility. For brownfield applications, VoR pertains to the operational
                                                                                        phase of the life cycle [8].
                                                                                        As the NOA concept strives to generate added value to an existing process automation system [9], [1], [7], VoR
                                                                                        imposes limits on what control loops it interacts with (see section 8.6.2 Communicating values to the CPC). Any
                                                                                        data made available through VoR should be considered volatile in regard to its quality, up-to-dateness and
                                                                                        availability. VoR may provide quality metrics to express this uncertainty where possible. Using VoR in any
                                                                                        manner that augments automation inside the CPC in a manner that makes safe and reliable production
                                                                                        dependent on VoR is not advised!
                                                                                        Finally, this document has an informative character for IT personnel and cybersecurity experts that need to
                                                                                        evaluate what VoR does and how it interacts with the IT/OT landscape.

                                                                                        Attacker, Attack
                                                                                             An attack is any unauthorized attempt to access, use, alter, expose, steal, disable, or destroy an asset [ISO
                                                                                             27000] within the CPC. An attacker is a person, group of interest or organization that executes the attack.

                                                                                        CPC Endpoint
                                                                                           A data object (control system variable, container, file, device parameter, etc.) known to and used with CPC
                                                                                           devices or systems.

                                                                                        DMZ (demilitarized zone)
                                                                                           physical or logical sub-network that contains and exposes an organization's external-facing services to a
                                                                                           larger and un-trusted network, usually the Internet. (ISO 16425:2024 glossary)

                                                                                            perimeter network (also known as a screened sub-net) inserted as a “neutral zone” between networks.
                                                                                            (ISO/IEC 27033-1:2015 glossary)

                                                                                        6.        VoR architecture overview and key concepts
                                                                                        The NOA Verification of Request is a system-of-systems architecture that transports information from the psM+O
                                                                                        to the CPC domain. By design, VoR interdicts direct communications between these domains. Instead, the
                                                                                        request issuer hands off the request to the VoR component, which performs a specific sequence of steps. These
                                                                                        verify that the request is trustworthy, feasible, beneficial to the process, can be mapped to the plant’s automation
                                                                                        technology and that changes occur at an opportune moment. During this process, the requested changes are
                                                                                        transformed in a manner facilitating its plant-specific integration. This transformation is not visible to the psM+O
                                                                                        domain, preserving and protecting plant-specific intellectual property.
                                                                                        Most VoR steps model an expert system using rule-based mechanisms. Experts (humans) program the VoR
                                                                                        steps by describing actions they would perform to establish that requested changes are beneficial, safe,
                                                                                        repeatable and automatable. The sequence of steps is derived by examining the manual process that would be
                                                                                        used to implement requests for change without VoR. Each step corresponds to an expert’s domain knowledge.
                                                                                        VoR supplements existing control systems inside the CPC. It provides means by which an external request is
                                                                                        presented to these systems for their consideration. VoR may be regarded as a component that closes a greater
                                                                                        NOA information loop: data sourced from CPC [4] are annotated [11], processed, transformed, supplemented
                                                                                        with additional information and then reintegrated into the CPC by VoR. Section 8.7 details which kinds of
                                                                                        automation control loops should be augmented in this manner.

                                                                                        VoR does not describe the technical systems or reference implementation used to implement its steps. Some
                                                                                        of the VoR’s steps inherently need to be implemented using technical systems located within the CPC or the
                                                                                        psM+O. Typical CPC components that can perform VoR steps include AMS, PCS or DCS. By implementing
                                                                                        NOA steps, these systems would become part of the VoR.

                                                                                                  Information flow through VoR
                                                                                        This Recommendation strongly advocates that there should not be any direct data connection between the
                                                                                        psM+O domain to the CPC or vice versa. Instead, VoR relays information between these domains in a strict,
                                                                                        predetermined manner. VoR considers two types of information flows: request flows and feedback flows (see
                                                                                        Figure 2). While information traverses VoR, data is exclusively inspected by VoR’s steps and is forwarded in a
                                                                                        specific sequence and direction.
                                                                                        Requests are abstract, but well-defined messages sent by a request issuer located in the psM+O domain,
                                                                                        suggesting an alteration in the current plant operations with a beneficial intent. Request information can solely
                                                                                        flow from the psM+O domain to the CPC domain as a result of forwarding data between request processing
                                                                                        steps in a specific sequence. VoR does not create requests. Steps are introduced in section 6.3 Request
                                                                                        processing sequence and detailed in section 7.
                                                                                        Feedback flows convey a processing status of an issued and received request to the issuer of the request.
                                                                                        Feedback is always created by and at the discretion of VoR processing steps and forwarded to the request

                                                                                                                                           Page 12 of 59

                                                                                        issuer as a result of forwarding data between feedback processing steps in a specific sequence. Feedback is
                                                                                        discussed in section 6.4 Feedback processing sequence and detailed in section 7.

                                                                                                  VoR architecture overview
                                                                                        VoR is composed of multiple technical systems that implement the processing steps (see sections 6.3 and 6.4).
                                                                                        Both steps and technical systems must be attributed to a domain, called ‘module’ as per NE 177 [4]. The
                                                                                        terminology and principal design of the NE 177 domain transition concept [4] – i.e., having 3 discrete modules
                                                                                        as a domain transition – is intentionally reused as a classification scheme for the domain transition in VoR.
                                                                                        Modules define where it is safe to conduct specific information processing steps or operate technical systems
                                                                                        that implement steps (see section 6.6 Attribution of steps to security zones). Modules are not physical
                                                                                        components.
                                                                                        Like a NOA gateway, VoR partitions the domain transition concept into three modules (modules 1-3) [4].
                                                                                            1. Any technical system or step attributed to module 1 is located in the CPC domain and security zone.
                                                                                            2. Any technical system or step attributed to module 2 is considered to reside in a demilitarized zone (DMZ)
                                                                                               dedicated to VoR. This module is explicitly distinct from either psM+O or CPC domains.
                                                                                            3. Any technical system or step attributed to module 3 is located in the psM+O domain.
                                                                                        Request information flows traversing the VoR must pass through all three modules in descending order (3-2-1).
                                                                                        In particular, it is not permissible to bypass module 2. This information flow is the reverse of that found in a NOA
                                                                                        Gateway.
                                                                                        Feedback flows generated by VoR steps must flow through modules in ascending order, starting from the
                                                                                        module in which the feedback was generated by its associated request processing step.

                                                                                                  Request processing sequence
                                                                                        Verification of a request entails repeated checks of the request contents to ensure that it is applicable to the
                                                                                        process, that it is safe and that it is trustworthy. This is accomplished by subjecting the contents of a request to
                                                                                        a series of verification and transformation steps.
                                                                                        These steps are introduced and summarized here. Each step, its information interface and the feedback it
                                                                                        generates are detailed in section 7 VoR request processing steps and feedback steps.
                                                                                        The steps performed by VoR are described in the order they are applied to the information within a request.
                                                                                        Authentication & Authorization. The authorization step accepts a request originating in the M+O domain and
                                                                                        ensures authorization of the issuer (e.g., by verifying its credentials, whitelists or certificates) and integrity of the
                                                                                        request (e.g., by means of checksums or electronic signatures). This requires the request issuer to first
                                                                                        authenticate themselves to the VoR. This step is also responsible for ensuring confidentiality of communications
                                                                                        with the request issuer by mandating that requests must be submitted using encrypted communications.
                                                                                        Request Verification. During this step the VoR ensures the request formulated by the issuer is reasonable,
                                                                                        achievable, acceptable and safe for the plant. If, for instance, a request issuer requests the temperature of a
                                                                                        reactor to be decreased by 10 Kelvin, this step would ensure that this is reasonable and beneficial for the process
                                                                                        to do and to achieve. This step may also include boundaries as to the frequency of requests an issuer may
                                                                                        submit, mandate a specific time during which this issuer may submit requests, etc.
                                                                                        Mapping. The issuer of the request formulates a suggested change to a process. The mapping step describes
                                                                                        how this change affects specific CPC endpoints within the plant. A CPC endpoint is any data object (control
                                                                                        signals, configuration value, etc.) that is known to the established automation. To realize, for instance, the 10
                                                                                        Kelvin temperature change in the reactor, several control signals may need to be changed. Any changes
Normen-Download-DIN Media-Imrane NEJAM-KdNr.8456219-LfNr.11476178001-2025-05-16 12:42




                                                                                        suggested by the mapping step to one or more CPC endpoints do not take effect until the mapping verification
                                                                                        step is completed.
                                                                                        Acceptance. Acceptance considers if a requested change to mapped CPC endpoints is possible and beneficial
                                                                                        in regard to the current state of the process. Acceptance may be manual (e.g., reviewed and acted upon by an
                                                                                        operator) or automated. It may be additionally tied to specific conditions, such as the presence of key personnel,
                                                                                        time of day, etc. As an example, the suggested change to the reactor temperature may need to be deferred until
                                                                                        the current product batch has been completed. Alternatively, the process may currently be under maintenance,
                                                                                        making its optimization impossible. Acceptance is always tied to the traceability of changes and must be
                                                                                        implemented as a VoR step, even if acceptance of a request is automated or unconditional.
                                                                                        Mapping Verification. After the effect of a request on the plant’s control variables is known, the range and
                                                                                        effect of this change are verified. This ensures that specific control loop parameters, device configurations, etc.
                                                                                        are correct, e.g., with regard to control loop stability or numeric ranges. This step examines changes with regard
                                                                                        to uo-to-date parameters and may involve checking highly specific and technical aspects of the automation,
                                                                                        such as PID stability criteria. This step is considered to be entirely automated.
                                                                                        Propagation. As per section 6.2, the request must be explicitly propagated between psM+O and CPC. Next to
                                                                                        security, this is also required because the existing CPC will use established, possibly plant-specific protocols or
                                                                                        technologies (e.g., when implementations of VoR are integrated into a PCS). The propagation step



                                                                                                                                             Page 14 of 59
                                                                                        NE 178                              NOA Verification of Request                           Version 2025-03-10



                                                                                        communicates VoR concepts in any technology available or suitable in the CPC and the target technical
                                                                                        system(s).
                                                                                        Propagation may be conducted at any time after authorization and authentication but must occur before
                                                                                        acceptance.
                                                                                        All steps mentioned above must ensure traceability of actions, information flows and decisions, with particular
                                                                                        emphasis placed on any information that reached the mapping verification step.

                                                                                                 Feedback processing sequence
                                                                                        VoR steps may supply the issuer with feedback concerning the request submitted.
                                                                                        The feedback mechanism should not leak information that is not directly related to the processing status of a
                                                                                        request. As an example, detailing that a human operator denied a request because of ongoing maintenance
                                                                                        tasks leaks information both of the presence of personnel and the operational status of the plant. To avoid this,
                                                                                        each step should only generate specific feedback messages detailed in section 7.
                                                                                        Feedback is treated as out-of-band communications in regard to request submission, meaning that VoR will
                                                                                        send feedback using a different communication mechanism than request submission. Instead, VoR will send
                                                                                        feedback to the issuer when and if it becomes available - potentially with considerable delays if human
                                                                                        intervention is involved.
                                                                                        Steps in modules 1 and 2 may not know from what peer the request has originated - they may associate
                                                                                        feedback only with a unique request identifier supplied by the VoR. The association of this identifier with a
                                                                                        specific peer may only occur in module 3.
                                                                                        Feedback is always created by VoR steps and always relates to a specific request that was submitted. Feedback
                                                                                        always addresses the status of requests before they are put into effect. Feedback MAY NOT be created by CPC
                                                                                        systems that do not implement VoR steps.
                                                                                        Feedback is processed by implementing the following steps in order:
                                                                                        Feedback Submission: A VoR step submits feedback to be forwarded to the request issuer. Submission
                                                                                        ensures that the submitter of the feedback is entitled to do so and that all required information to formulate
                                                                                        feedback is submitted. A VoR may have submission steps in multiple modules to receive feedback from each
                                                                                        step.
                                                                                        Feedback Verification: Verifies that the feedback pertains to valid requests and that the request issuer is
                                                                                        entitled to receive feedback. Further limitations may apply, for examplehow long ago the request was received
                                                                                        or if the issuer is on or off premises.
                                                                                        Feedback Dispatch: Feedback is dispatched (sent) from the VoR to the issuer in a way supported by the issuer.
                                                                                        This step associates the request ID referenced by the feedback message with the specific connection
                                                                                        parameters and technologies needed to deliver the message.

                                                                                                 Rule-based automation of steps
                                                                                        Steps introduced for processing requests and feedback are expected to be largely automated using rule-based
                                                                                        systems. The key goal is to create a maintainable, repeatable and automated way to verify, map and accept
                                                                                        requests and feedback.
                                                                                        Notable exceptions are the following steps that are considered configuration-based, not rule-based: Request
                                                                                        Authentication & Authorization, Request Propagation, Feedback Submission and Feedback Dispatch.
                                                                                        Rules are formulated by domain experts, usually experienced on-site personal. In this sense, VoR constitutes
                                                                                        an OT expert system. The description format and language are vendor- and domain-specific. A single VoR may
                                                                                        use multiple different ways to describe rules.
                                                                                        Rules, once formulated, are stored by VoR and can be accessed by the specific steps they were designed to
                                                                                        automate. Additionally, rules may require specific request properties, e.g., the request origin or expected data
                                                                                        contained in the request. After that, the rules are processed automatically by the respective step.
                                                                                        Rule-based processing steps are considered automated. Human interaction conceptually occurs by adding or
                                                                                        removing rules, thereby expanding the expert system. In isolated scenarios, rules may prompt human interaction
                                                                                        (see section 8.6.4 Interaction between OT personnel and VoR).

                                                                                                  Verification step
                                                                                        The verification step examines the request in regards to plausibility for the process and is considered an
                                                                                        automated step. The VoR owner’s/operator’s process experts specify a set of rules that are associated with a
                                                                                        request issuer and additional (fixed) request characteristics. As a result of successful request verification, rules
                                                                                        will either deny or accept the request.
                                                                                        The request verification step must be situated in either the DMZ (module 2) or psM+O (module 3) security zones.
                                                                                        The request verification step always takes place after the authentication and authorization step and before the

                                                                                        8.        Designing, operating and maintaining VoR systems

                                                                                                  Information interfaces
                                                                                        Each step described in section 7 VoR request processing steps and feedback steps specifies what information
                                                                                        it requires as input. Beyond that, this Recommendation has no intention of specifying a specific information
                                                                                        model or specific formats or technologies. Definitions of protocols, models, data fields, data types, etc. are
                                                                                        subject to the communication technology employed by the VoR implementation.
                                                                                        In the spirit of an open architecture, it is imperative that a solution deemed ‘to implement and adhere to the NOA
                                                                                        VoR recommendation’ can be used by all stakeholders in a NOA ecosystem. Any VoR implementation should
                                                                                        be technologically accessible to vendors of optimization solutions, edge & cloud service providers as well as the
                                                                                        owner/operator of a plant.
                                                                                        To guarantee this in a technology-agnostic, vendor-independent manner, any solution that considers itself VoR-
                                                                                        compliant must ensure that the following principles apply:
                                                                                             1. The technological means of communicating with (submitting information to/receiving information from)
                                                                                                any VoR step that is accessible to more than one intellectual property holder (vendor)
                                                                                                     a. must be built on open communication technologies,
                                                                                                     b. must provide public documentation on their use, specifically on how to submit the information
                                                                                                        to this specific step in a valid fashion;
                                                                                             2. the Authentication and authorization step must fulfill the requirements of the previous principle 1;
                                                                                             3. if implemented, the Feedback dispatch step must fulfill the requirements of the previous principle 1;
                                                                                             4. further steps may fulfill principle 1 if they are designed to interact with the systems of another vendor.

                                                                                                  Configuration of VoR
                                                                                        VoR is an IT system-of-ystems architecture. As such, VoR is administered, supervised and maintained as an IT
                                                                                        system. But VoR is also an OT expert system for the automation of OT operations. As such, it is configured and
                                                                                        maintained as an OT system.
                                                                                        Any deployed VoR instance is required to provide technical means and interfaces for its configuration,
                                                                                        supervision and maintenance.
                                                                                        Information processing and feedback processing steps are expected to have limited read-only access to the
                                                                                        configuration elements that are essential for their operation on an as-needed basis. Steps detailed in section 7
                                                                                        VoR request processing steps and feedback steps should never be able to modify configurations themselves or
                                                                                        gain access to configuration interfaces that provide such capabilities.
                                                                                        To ensure the protection of VoR and the CPC that it shields, it is important that it is configured in an inside-out
Normen-Download-DIN Media-Imrane NEJAM-KdNr.8456219-LfNr.11476178001-2025-05-16 12:42




                                                                                        way. The management interface that is enabled for configuring must either be integrated into the CPC
                                                                                        environment or into a dedicated separate network. It must be prevented that an attacker can open a backdoor
                                                                                        in VoR from the ‘outside’ (M+O level or above).
                                                                                        Access to interfaces is subject to the NOA EXTENDED security profile as per NE 176 ([12]) as detailed in section
                                                                                        8.5.2 Protection profile of NOA Verification of Request.
                                                                                        Additionally, access to configuration elements needs to be restricted to authorized personnel only. For all
                                                                                        configuration elements installed, the VoR needs to assign
                                                                                             •   access rights,
                                                                                             •   access roles,
                                                                                             •   and mainly the check rules to be applied to requests.
                                                                                        It is highly recommended that VoR provides means for a four-eyes principle to comply with requirements for
                                                                                        critical plants. Management roles must then be created carefully to enable request-and-approve processes.
                                                                                        As the NOA VoR is located close to the CPC and transmitted information can change the CPC’s behavior, it has
                                                                                        to be included to the plant’s management of change processes.

                                                                                                  Monitoring and supervision of VoR as an information system
                                                                                        Monitoring and supervision of a VoR are essential to give plant operation staff a permanent, transparent insight
                                                                                        into and how and what information is automatically ingested by the CPC. Concurrently, activity logs are recorded
                                                                                        to conform with traceability requirements for retrospective analysis, e.g., audits.
                                                                                        It is highly recommended for VoR implementations to
                                                                                            •   record each activity with relevant information to be used for audits and security forensics;
                                                                                            •   feed activity recording into an intrusion detection system to recognize abnormal patterns (e.g.,
                                                                                                compromised issuer attacking/brute-forcing the VoR until it accepts solutions).
                                                                                        A clear indicator shall show the current working status of VoR to plant operators. This mechanism should also
                                                                                        allow inspecting what information is processed and transmitted to the CPC. It should also point out potential
                                                                                        errors and misconfigurations. If required, it may also provide means to intervene. The indicator is a core means
                                                                                        to build trust with the operating personnel and in emergency cases provides the decision-making basis for
                                                                                        manually inhibiting VoR from changing the CPC in order to protect plant operation and safety.
                                                                                        The feedback processing steps as outlined in sections 7.7, 7.8 and 7.9 enable the issuer of a request to receive
                                                                                        feedback about how the request was processed in general to ensure the proper functioning of the requesting
                                                                                        systems. Nevertheless, it is important not to disclose sensitive information to an attacker with fake requests. To

                                                                                                  Logging and keeping records
                                                                                        Traceability of any CPC change related to VoR to its origin (i.e., request issuer) is essential for the VoR concept.

                                                                                                  Communication between VoR steps and modules

                                                                                        be meaningful if the steps ‘authorization’ to ‘propagation’ are delivered with the M+O-applications whereas
                                                                                        ‘mapping’ to ‘mapping verification’ are implemented as an add-on to the CPC. Especially in this case, it is
                                                                                        essential that APIs are secure (see above) and well documented in their function and data structures.

                                                                                                  Security considerations
                                                                                        As VoR is a security-critical component at the border of a CPC, the interfaces used by the VoR-modules need
                                                                                        to be carefully designed. Propagating information from outside the M+O domain into the CPC domain inherently
                                                                                        introduces the risk of unintentional or even malicious harm to plant operations. The effects may range from a
                                                                                        misconfiguration of a component (AMS, PCS, DCS) to components being compromised and under the control
                                                                                        of an attacker.
                                                                                        This section on VoR IT security covers three distinct parts:
                                                                                           I. Overall security guidelines,
                                                                                          II. specific design guidelines for VoR components and interfaces,

                                                                                                                                           Page 28 of 59
                                                                                        NE 178                               NOA Verification of Request                            Version 2025-03-10



                                                                                         III. VoR organizational requirements and relations with IT & IT security.
                                                                                                  Overall security considerations of and guidelines for VoR design and use
                                                                                        VoR, as a system of systems, should always operate on a zero-trust principle. Every communication between
                                                                                        technical systems that is in principle accessible to third parties requires protection according to state-of-the-art
                                                                                        IT security standards. It must be robust against denial-of-service-attacks, employ encryption and mandate
                                                                                        authentication of the communication partners. This applies to VoR-internal communication parties (e.g.,
                                                                                        propagation) as well as to external peers on the psM+O or M+O level.
                                                                                        It is highly recommended that any form of authentication and authorization of interacting personnel should apply
                                                                                        the following principles:
                                                                                            •   Active account management (i.e., obsolete accounts are deleted, passwords are complex and changed
                                                                                                frequently);

                                                                                            •   Roles are assigned as required – authorization as much as necessary and as limited as possible;

                                                                                            •   Credentials for authorization and authentication are stored, configured and maintained by a trusted
                                                                                                system that is protected from being compromised. This system should be distinct from the system that
                                                                                                implements the Authentication & Authorization step. This can also be attached to the identity and rights
                                                                                                management of the CPC;

                                                                                            •   Multifactor authentication prevents fake authentication. Trusted certificates should be used in addition
                                                                                                to personnel or functional credentials.

                                                                                        Being a security system, the creation and parsing of logfiles are essential to triggering alerts because of
                                                                                        malfunction or potential attacks. In addition to detecting and mitigating attacks from untrusted/external systems,
                                                                                        it is essential to prevent attacks from a compromised trusted system. This includes attacks originating from other
                                                                                        compromised systems within the CPC which should not be considered implicitly ‘safe’ or ‘trusted’.
                                                                                        An additional vector for attacks is legitimate, but compromises request issuers. These could suggest malicious
                                                                                        changes. The primary way to prevent such attacks is by defining effective VoR rule sets that can differentiate
                                                                                        between good and bad request content. For setpoint optimization, an algorithm could forecast a dynamic target
                                                                                        range of the next request. As soon as the new request is outside the calculated range, an alert is generated and
                                                                                        the request is denied.

                                                                                        recommended to create CPC endpoints within VoR that do not correspond to any parameter, object or value
                                                                                        known inside the CPC. Examples of why this might occur include diagnostic measurements by PAT devices or

                                                                                               Overview
                                                                                               Intent
                                                                                        The use cases described in this Annex were designed to challenge and examine the design decisions underlying
                                                                                        VoR. They served as valuable discussion aids for the design of VoR; while it is clear in retrospective that the
                                                                                        use cases are perfectly covered by the capabilities of VoR, this was certainly not the case throughout the design
                                                                                        process. Additionally, the use cases presented a common terminology and graphical notation that allowed the
                                                                                        Working Group to communicate aspects of VoR more efficiently.
                                                                                        The use cases formulated below also serve as ‘tests’ or design requirements that can be checked when this
                                                                                        Recommendation is amended to ensure that all design goals are met.
                                                                                        The Working Group opted for keeping the use cases in this Recommendation as examples of how VoR might
                                                                                        tackle some specific challenges. Note that the list of use cases are not exhaustive; many more applications of
                                                                                        VoR that are not covered by this Annex may exist.
                                                                                        To a reader versed in the state of the art and current challenges faced by the process industry, some use cases
                                                                                        may seem unrealistic, oversimplified or hypothetical. This is intentional: Some use cases are deliberately kept
                                                                                        simple, while others were engineered to focus on a particular capability of VoR. The use cases do not describe
                                                                                        the state of the art of the operating environment or the automation systems, but rather VoR as an information
                                                                                        system.
                                                                                        The intention of these use cases is not to provide prefabricated solutions for real-world production plants - this
                                                                                        would be far too specific to the technology environment and automation technologies of individual sites and
                                                                                        stakeholders. Instead, the use cases were engineered so that stakeholders can portray and discuss the use of
                                                                                        specific VoR capabilities they require to meet their complex real-world challenges. Details on specific
                                                                                        technologies and additional components of the respective operating environments have been deliberately
                                                                                        omitted.
                                                                                                Formulating use cases

                                                                                        Use cases should focus on a specific beneficial function or behavior that VoR can introduce to the CPC.

                                                                                        Each use case should not exceed 3 document pages in size and contain the following sections:

                                                                                            1. Optional: An abstract that summarizes the scenario
                                                                                            2. A description of what challenge the stakeholder faces, how the stakeholder aims to eliminate the
                                                                                               addressed shortcomings using VoR and what the resulting benefit to the CPC/plant is.
                                                                                            3. Identification of key characteristics
                                                                                                   o Each use case should summarize key design requirements that it generates for VoR.
                                                                                                   o Each use case should clearly identify actors that are of particular relevance to the use case.
